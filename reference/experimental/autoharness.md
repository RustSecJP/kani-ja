# ハーネスの自動生成 {#automatic-harness-generation}

[はじめの一歩](../../tutorial-first-steps.html)で書いた `estimate_size` のハーネスを思い出してください。
```rust
#[cfg(kani)]
#[kani::proof]
fn check_estimate_size() {
    let x: u32 = kani::any();
    estimate_size(x);
}
```

このハーネスは、まず `kani::any()` を使ってローカル変数 `x` を宣言し、次に引数 `x` で `estimate_size` を呼び出します。
多くの証明ハーネスは、この決まった形に従います。関数 `foo` を検証するには、`foo` の各引数について任意の値を作り、その引数で `foo` を呼び出します。

`autoharness` サブコマンドは、この観察を利用してハーネスを自動的に生成し、それに対して Kani を実行します。
Kani は、引数を非決定的に生成できる関数をクレートの中から探し（[ハーネスの生成](#generating-harnesses)を参照）、それらの関数のハーネスを生成して実行します。
これらのハーネスは Kani の内部にあるものです。つまり、Kani はあなたのソースコードを一切変更しません。

## 使い方 {#usage}
次のどちらかを実行します。
```
# cargo kani autoharness -Z autoharness
```
または
```
# kani autoharness -Z autoharness <FILE>
```

Kani が関数 `foo` の引数をすべて生成できる場合、`#[kani::proof]` ハーネスを生成して実行し、次のように表示します。

```
Autoharness: Checking function foo against all possible inputs...
<VERIFICATION RESULTS>
```

ただし、`foo` に[関数契約](./contracts.html)があることを Kani が検出した場合は、代わりに `#[kani::proof_for_contract]` ハーネスを生成し、契約を検証します。
```
Autoharness: Checking function foo's contract against all possible inputs...
<VERIFICATION RESULTS>
```

同様に、Kani は[ループ契約](./loop-contracts.html)の存在を検出し、それらを検証します。

そのため、`-Z autoharness` は `-Z function-contracts` と `-Z loop-contracts` を含意します。つまり、実験的な
autoharness フィーチャを有効にすると、関数契約とループ契約のフィーチャも有効にすることになります。

Kani はこれらのハーネスを内部で生成して実行します。ユーザに見えるのは検証結果だけです。

オプションの完全な一覧は、`kani autoharness --help` を実行して確認してください。

Rust 標準ライブラリそのものに対して autoharness を実行するには、単独コマンドに `--std` を渡し、
標準ライブラリのチェックアウト（[verify-rust-std](https://github.com/model-checking/verify-rust-std)
にあるものなど）の `library` ディレクトリを指定します。

```
# kani autoharness -Z autoharness --std <PATH>/library
```

パスは `library` という名前のディレクトリでなければなりません。Kani は、`kani verify-std` と同じように、
ターゲットディレクトリ内の一時的なクレートを通じて `cargo -Z build-std` でそれをビルドします。`--std` は
`kani autoharness` でのみ使え、`cargo kani autoharness` では使えません。

標準ライブラリを検証するときは、`core` で使える Kani の定義だけを利用できます。一部のモデルは完全な
`kani` ライブラリでしか使えません。`Box`、`Rc`、`Arc` の引数、有界でないプリミティブのスライスと `Vec`、
そして `Fn` 境界を持つ型パラメータのための関数モデルがそれにあたります。これらのモデルは `--std` では使えません。
影響を受ける引数は、`core` が有界な生成器を提供していて、かつ `--bounded-arguments` が渡されている場合は
有界な値で生成されます。そうでなければ、その関数はスキップされます。

具体的な再生（concrete playback, `-Z concrete-playback`）は `autoharness` サブコマンドではサポートされていません
（[#5109](https://github.com/model-checking/kani/issues/5109)）。

## 例 {#example}
もう一度、[はじめの一歩](../../tutorial-first-steps.html)の `estimate_size` の例を使います。
```rust
fn estimate_size(x: u32) -> u32 {
    if x < 256 {
        if x < 128 {
            return 1;
        } else {
            return 3;
        }
    } else if x < 1024 {
        if x > 1022 {
            panic!("Oh no, a failing corner case!");
        } else {
            return 5;
        }
    } else {
        if x < 2048 {
            return 7;
        } else {
            return 9;
        }
    }
}
```

次の結果が得られます（チェックごとの詳細が表示されるように `--output-format=regular` を渡しています。
[並列検証](#parallel-verification)を参照してください）。

```
# cargo kani autoharness -Z autoharness --output-format=regular
Autoharness: Checking function estimate_size against all possible inputs...
RESULTS:
Check 3: estimate_size.assertion.1
         - Status: FAILURE
         - Description: "Oh no, a failing corner case!"
[...]

Verification failed for - estimate_size
Complete - 0 successfully verified functions, 1 failures, 1 total.
```

## 関数の選択 {#selecting-functions}

autoharness は、検証対象のクレートで定義された関数を対象にします。これには、自由関数、固有メソッド、トレイト実装のメソッド、デフォルト実装を持つトレイトメソッドが含まれます。依存先のクレートの関数は候補になりません。対象となる関数ごとに、Kani は自動ハーネスを 1 つ選びます。選択チェックに失敗した関数はスキップされます。`--quiet` が指定されていない限り、Kani は検証の前に、選ばれた関数と、表示対象のスキップ理由を報告します。

候補の関数は、それぞれ決まった順序で選択チェックを受け、最初に失敗したチェックがスキップ理由になります。Kani 内部の関数とコンパイル時専用の関数は、ジェネリックのインスタンス化より前に除外されます。次に、ジェネリックな関数がインスタンス化されます（[ジェネリックな関数](#generic-functions)を参照）。インスタンス化された関数は、順に、本体があるか、証明ハーネスや Kani のトレイト実装ではないか（そうであれば除外）、include パターンと exclude パターンに一致するか、サポートされていない呼び出し規約ではないか、そして最後に引数を生成できるかをチェックされます。引数の生成の詳細は[ハーネスの生成](#generating-harnesses)で説明します。

### include パターンと exclude パターン {#include-and-exclude-patterns}

`autoharness` サブコマンドには、正規表現を使って特定の関数を含めたり除外したりするための `--include-pattern [REGEX]` と `--exclude-pattern [REGEX]` オプションがあります。
照合のとき、Kani は関数のパスの先頭にクレート名を付けます。たとえば、`my_crate` クレートにあるジェネリックでない関数 `foo` は `my_crate::foo` として照合されます。
選択のアルゴリズムは次のとおりです。
- `--include-pattern` だけが与えられた場合、与えられたパターンのどれかに一致する関数を含めます。
- `--exclude-pattern` だけが与えられた場合、与えられたパターンのどれにも一致しない関数を含めます。
- 両方が与えられた場合、include パターンに一致し、*かつ* どの exclude パターンにも一致しない関数を含めます。これは exclude パターンが優先されることを意味します。つまり、関数が include パターンと exclude パターンの両方に一致する場合、その関数は除外されます。

いくつか例を示します。

```bash
# foo を含み bar を含まない関数を含める
kani autoharness -Z autoharness --include-pattern 'foo' --exclude-pattern 'bar'

# my_crate::foo だけを正確に含める
kani autoharness -Z autoharness --include-pattern '^my_crate::foo$'

# foo モジュール内の関数を含めるが、foo::bar 内のものは含めない
kani autoharness -Z autoharness --include-pattern 'foo::.*' --exclude-pattern 'foo::bar::.*'

# test_ で始まる関数を含めるが、private モジュール内にあるものは含めない
kani autoharness -Z autoharness --include-pattern 'test_.*' --exclude-pattern '.*::private::.*'

# foo::bar に一致するものはすべて bar も含むので、結局何も含まれない。
# Kani はこれらのオプションが矛盾しているという警告を出す。
kani autoharness -Z autoharness --include-pattern 'foo::bar' --exclude-pattern 'bar'
```

Kani は関数のパスの先頭にクレート名を付けるので、パターンによっては思ったより多くのものに一致することがあります。
たとえば、クレート `my_crate` の中に関数 `foo_top_level` があるとき、正規表現 `.*::foo_.*` は `foo_top_level` に一致します。Kani はこれを `my_crate::foo_top_level` として解釈するからです。
モジュール内の `foo_` 関数だけに一致させるには、`.*::[^:]+::foo_.*` のように、より具体的なパターンを使ってください。

パターンは、ジェネリックな関数の**インスタンス化後の名前**に対して照合されます。たとえば、`my_crate::foo::<i32>` は `^my_crate::foo$` には一致しませんが、アンカーのない `foo` パターンには一致します。正規表現は、明示的にアンカーを付けない限りアンカーなしです。不正な正規表現と、空白を含むパターンは拒否されます。また、include パターンの文字列が exclude パターンの文字列を含む場合、Kani は警告を出します。

ジェネリックのインスタンス化は、include/exclude による絞り込みより前に行われます。そのため、Kani がインスタンス化を見つけられないジェネリックな関数は、与えられたフィルタに一致しない関数であっても、`Generic Function` というスキップ理由で報告されます。コンパイル時専用の関数も同様で、こちらはインスタンス化よりもさらに前に除外されます。

### 関数の一覧表示 {#listing-functions}

autoharness は `--list` も受け付けます。これはプロジェクトをコンパイルし、自動ハーネスを含めて [list サブコマンド](../list.html)を実行しますが、**検証は実行しません**。`--quiet` が渡されていない限り、Kani はまず、選ばれた関数とスキップされた関数の表を表示します。

出力形式を選ぶには `--list --format <FORMAT>` を使います。

| 形式 | 出力 |
| --- | --- |
| `pretty`（デフォルト） | 一覧を端末に表示します。 |
| `markdown` | カレントディレクトリに `kani-list.md` を書き出します。 |
| `json` | カレントディレクトリに `kani-list.json` を書き出します。 |

ファイルに書き出す形式では、Kani は書き出したファイルのパスを表示します。`--format` オプションには `--list` が必要です。`--quiet` と `--list --format pretty` の組み合わせはサポートされていません。

たとえば次のようにします。

```bash
# 検証せずに関数とハーネスを一覧表示する
cargo kani autoharness -Z autoharness --list

# 一覧を JSON として書き出す
cargo kani autoharness -Z autoharness --list --format json
```

### スキップ理由 {#skip-reasons}

autoharness は、スキップされた関数ごとに 1 つのスキップ理由を記録します。それは、その関数の選択過程で最初に失敗したチェックです。スキップされた関数の表には `Crate`、`Skipped Function`、`Reason for Skipping` の列があります。ユーザに見える理由には、チェックが実行される順に次のものがあります。

| 表示される理由 | 意味 |
| --- | --- |
| `Can only be called at compile time` | その関数はコンパイル時に実行するよう指定されているため、自動ハーネスの対象に選べません。 |
| `Generic Function: <detail>` | 関数の制約を満たす、サポートされたインスタンス化を Kani が見つけられませんでした。detail は具体的な原因を示します。[ジェネリックな関数](#generic-functions)を参照してください。 |
| `The function does not have a body` | 検証できる関数本体がありません。デフォルト実装のないトレイトメソッドなどがこれにあたります。 |
| `Did not match provided filters` | その関数は include/exclude パターンによって除外されました。 |
| `Explicit tail calls are not supported` | 関数本体に明示的な末尾呼び出し（`become`）が含まれていますが、Kani はこれをサポートしていません。 |
| `Unsupported variadic calling convention` | その関数は C の可変長引数関数で、Kani がモデル化できない呼び出し規約を使っています（たとえば `extern "sysv64"`）。 |
| `Missing Arbitrary implementation for argument(s) x: T, y: U` | 少なくとも 1 つの引数が、サポートされた引数モデルで生成できません。引数の名前と型は関数によって異なります。 |
| `Requires --bounded-arguments for argument(s) x: T` | 少なくとも 1 つの引数で、有界な生成を有効にする必要があります。引数の名前と型は関数によって異なります。 |

名前のない引数は `_` と表示されます。サポートされていない引数と、有界な生成が必要な引数の両方を持つ関数では、スキップ理由として `Missing Arbitrary implementation` が報告されます。サポートされている引数モデルについては[ハーネスの生成](#generating-harnesses)を、オプトインの動作については[有界な引数](#bounded-argument-generation)を参照してください。

Kani の内部実装の関数や、すでに証明ハーネスとして使われている関数は、内部的に `Kani implementation` という理由で除外されることがありますが、これらの項目はスキップされた関数の表には**表示されません**。選ばれた関数の表には `Crate` と `Selected Function` の列があります。ジェネリックのインスタンス化が選ばれた場合、表にはインスタンス化後の関数名（たとえば `foo::<i32>`）が表示されます。インスタンス化できないジェネリックな関数は、インスタンス化前の名前で表示されます。

### ジェネリックな関数 {#generic-functions}

ジェネリックな関数について、Kani は**単一の単相的なインスタンス化**に対するハーネスを生成します。つまり、関数の型パラメータを具体的な型で置き換え、そのインスタンス化がトレイト境界と `where` 節を満たすことを要求し、ライフタイムパラメータを消去します。

Kani はまず、次のプリミティブ型を候補として、すべての型パラメータに同じ型を使って試します。`i32`、`u32`、`usize`、`u8`、`i64`、`u64`、`f64`、`f32`、`bool`、`char` です。一律の選択でうまくいかない場合は、個々のパラメータについて候補の型の組み合わせを探索します。候補にはプリミティブ型に加えて、パラメータのトレイト境界の実装から導かれた最大 16 個の具体的な型（たとえば、クレート内のトレイトを実装するクレート内の構造体）が含まれることがあります。この組み合わせ探索は 256 回の試行に制限されています。適切なインスタンス化が見つからなければ、Kani は最後に、すべての型パラメータに `()` を使って 1 回だけ試します。

たとえば、次のコードがあるとします。

```rust
fn foo<T: Eq>(x: T, y: T) {
    if x == y {
        panic!("x and y are equal");
    }
}
```

Kani は `foo::<i32>` を検証するハーネスを生成して実行し、要約の表にはインスタンス化後の名前が表示されます。たとえば次のとおりです。

```text
| Crate    | Selected Function | Kind of Automatic Harness | Verification Result |
| my_crate | foo::<i32>        | #[kani::proof]            | Failure             |
```

単一のインスタンス化を検証することは、関数がとりうるすべての振る舞いの過小近似です。`foo::<i32>` で成功したからといって、`foo` の他のインスタンス化も安全であるとは限りません。Kani は、選んだインスタンス化の名前を表示することで、それを明示します。この制限が何を意味するかについては、[単一の単相化](#single-monomorphization)を参照してください。

**const ジェネリックパラメータ。** 配列の長さなどの `usize` の const ジェネリックパラメータは値 `2` でインスタンス化されるので、インスタンス化後の関数名に `::<2>` が含まれることがあります。他の型の const ジェネリックパラメータは、現在サポートされていません。また、const ジェネリックパラメータが、その評価によってそのパラメータが制約されうる `const {}` ブロック（たとえば `const { assert!(N >= 4) }`）に到達しうる場合も、Kani はその関数をスキップします。このチェックは保守的です。不正なコンパイル時評価の危険を冒すよりも、置き換えた値がアサーションを満たす場合でも、Kani は関数をスキップすることがあります。

**関数トレイトの境界。** `Fn`、`FnMut`、`FnOnce` で境界づけられたパラメータについては、Kani はジェネリックな関数をスキップする代わりに、非決定的な関数モデルを試すことがあります。モデルがサポートするのは、値渡しの入力 0 個から 3 個、または共有参照を含む入力 1 個から 2 個（参照と値の引数の混在を含む）です。リターン型は `Arbitrary` を実装していなければなりません。結果として得られる境界が満たせるなら、ジェネリックな関数の他の型パラメータが関わるシグネチャに対してもモデルを選べます。使える適切なモデルがない場合、その関数はジェネリックな関数としてスキップされることがあります。このモデルの振る舞いと制限については、[Fn 境界を持つクロージャ](#fn-bound-closures)を参照してください。

**その他のインスタンス化の失敗。** 境界を満たす候補がない場合や、インスタンス化の探索が上限に達した場合、Kani はジェネリックな関数をスキップすることがあります。また、関数自身の本体で、互換性のない非 SIMD 型や不正な SIMD 比較結果型を使って `simd_*` 組み込み関数を呼び出すことになる候補のインスタンス化も拒否します。その場合でも、別の有効な候補が選ばれることはあります。`Generic Function` のスキップ理由の detail は、該当する失敗を示します。これには、サポートされていない const ジェネリクス、const ジェネリクスの前提条件、SIMD の制約、探索試行の使い切り、満たされないトレイト境界が含まれます。

ジェネリックな関数を呼び出す側のどれかが自動ハーネスの対象になれば、そのジェネリックな関数の他の単相化されたバージョンにも、呼び出し側のハーネスを通じて到達する（つまり検証される）ことがあります。

Kani が関数を選び、必要ならインスタンス化を選んだ後は、[ハーネスの生成](#generating-harnesses)で説明するとおりにハーネスの引数を生成します。

## ハーネスの生成 {#generating-harnesses}

### 引数 {#arguments}

#### 有界でないもの（デフォルト） {#unbounded-default}

Kani は、`--bounded-arguments` を必要とせずに、デフォルトで次の引数生成器を使います。
それぞれがサポートする型とモデル化の限界は以下で説明します。

##### Arbitrary を実装する引数 {#arguments-implementing-arbitrary}
Kani は、関数の各引数を非決定的に生成できるとき、自動ハーネスを生成します。
[`Arbitrary`](../arbitrary.html) を実装する引数には `kani::any()` を使います。そのような型への共有参照や
可変参照については、参照先の型の値を、ハーネス全体にわたって生存するストレージに生成し、その参照を渡します。

`Arbitrary` 実装を持たない、サポートされた構造体と列挙型については、Kani はフィールドを生成し、
列挙型ならバリアントを非決定的に選ぶことで、実装を合成できます。private なフィールドもサポートされますが、
フィールドの生成には追加の制限があります。むき出しの参照フィールドと `NonNull` フィールド
（`Option<NonNull<T>>` のようなラッパを含む）は合成されず、ライフタイム引数を持つ型は自動導出を使えません。
その他のフィールドは `Arbitrary` を実装しているか、再帰的な導出の要件を満たしていなければなりません。
自動導出は autoharness でのみ使え、型に derive アトリビュートを追加する必要はありません。
以下の引数モデルによって、サポートされていないフィールドの型が導出可能になることはありません。

以下の節では、追加の引数モデルを説明します。有界な生成器が必要な型については、
[有界な引数](#bounded-argument-generation)で扱います。

##### 生ポインタ {#raw-pointers}
生ポインタの引数（`*const T`/`*mut T`、入れ子になった生ポインタを含む）を持つ関数については、
参照先の型が `Arbitrary` を実装している（または導出できる）場合、生成されるハーネスは非決定的な
割り当て状態のポインタを作ります。生成される各ポインタはアラインされていて、次のいずれかです。
- null
- 割り当ての範囲外（したがって読み書きには不正）
- 有効。参照先の型の非決定的な値を指し、その値はハーネス全体にわたって割り当てられたままです。

そのため、null の状態と範囲外の状態を排除できないまま生ポインタの引数を参照外しする関数は、
検証に失敗します。安全な関数では、このような失敗は本当の堅牢性の問題を示しています。安全なコードは
どんなポインタ値でも渡せるからです。安全性が呼び出し側の義務に依存する関数（たとえば、文書化された
前提条件を持つ `unsafe fn`）では、`#[kani::requires(kani::mem::can_dereference(ptr))]` のような Kani の
[メモリ述語](https://model-checking.github.io/kani/crates/doc/kani/mem/index.html)を使って
[関数契約](contracts.html)を追加してください。自動の契約ハーネスはその事前条件を仮定するので、
不正なポインタの状態は除外されます。

生成されるポインタの現在の制限は次のとおりです。
- ポインタは常にアラインされています。アラインされていないポインタのバグは対象外です。
- 解放済みのオブジェクトへのポインタは生成されません（Kani のメモリ述語はそれについて推論できません）。
- 異なるポインタ引数どうしが別名になる（エイリアスする）ことはなく、有効な状態では参照先は常に初期化されています。
- 生ポインタは直接の引数としてのみサポートされます（他の生ポインタの中に入れ子にするのは可）。参照の先や
  ユーザ定義型の中にあるものはサポートされません。

##### Box、Rc、Arc {#box-rc-and-arc}

`Box<T>`、`Rc<T>`、`Arc<T>` の引数は、サイズが既知の参照先の型 `T` が `Arbitrary` を実装しているか、
Kani がそれを自動的に導出できる場合にサポートされます。Kani は非決定的な参照先を生成し、それを包む
新しいスマートポインタを構築します。これらの引数には `--bounded-arguments` フラグは不要で、
"(bounded)" マーカーも付きません。

これらの生成モデルは割り当てのサポートを必要とし、デフォルトのアロケータを使います。モデルが網羅するのは
参照先の生成された値です。`Rc` と `Arc` は強参照 1 つ、弱参照 0 から始まるので、他の所有者や弱参照が
存在する状態は探索されません。そのため、生成された値に `Rc` や `Arc` を直接、または入れ子で
（たとえば `Box<Rc<T>>`、`(u8, Rc<T>)`、`&Arc<T>`、`Arc` フィールドを持つ構造体）含むハーネスには、
"(refcount)" マーカーが付きます（[要約の表とマーカー](#summary-table-and-markers)と
[参照カウント](#reference-counts)を参照）。`str` や `[T]` のようなサイズが不定の参照先は、これらの
モデルの対象外です。`Box<[T]>` のような一部の型は、代わりに `--bounded-arguments` を指定して
`BoundedArbitrary` を通じて生成できます。

##### プリミティブのスライスと Vec {#primitive-slices-and-vec}

直接の `&[T]`、`&mut [T]`、`Vec<T>` の引数は、`T` がプリミティブの整数型または浮動小数点型
（たとえば `u8`、`i32`、`f64`）であるとき、長さの上限なしで生成されます。各引数は、非決定的な長さと
内容を持つ新しい割り当てを使います。長さを制限するのは、Rust の割り当てサイズの要件だけです。
可変スライスは排他的な裏付けストレージを持ちます。生成される `Vec` はグローバルアロケータを使い、
容量は `len.max(1)` です。

これらのモデルは割り当てのサポートを必要とします。デフォルトで有効で、"(bounded)" マーカーは付かず、
`--bounded-arguments` が渡された場合でも有界な生成より優先されます。`--slice-bound` と
`--bounded-arbitrary-bound` はこれらを制限しません。`bool`、`char`、`NonZeroU32`、ユーザ定義の構造体
などの要素型では、サポートされていれば代わりに有界な生成器が使われます。

引数の長さが有界でなくても、ループの展開の上限がなくなるわけではありません。入力を反復処理する関数は、
その上限が足りなければ展開アサーションに失敗することがあります。[ループの展開](../../tutorial-loop-unwinding.html)
を参照してください。`&&[u8]` のような入れ子のスライス参照や、ユーザ定義型の中のスライスは、これらの
引数モデルの対象外です。

##### Fn 境界を持つクロージャ {#fn-bound-closures}

`Fn`、`FnMut`、`FnOnce` で境界づけられた、サポートされたジェネリックパラメータについては、Kani は
呼び出しのたびに新しい `kani::any()` の値を返す関数アイテムを与えます。リターン型は `Arbitrary` を
実装していなければなりません。同じ入力に対しても、呼び出しを繰り返すと異なる値が返ることがあります。
関数アイテム自体には `Arbitrary` 実装は必要ありません。

モデルは、値渡しの引数 0 個から 3 個をサポートします。共有参照の入力については、共有参照と値の混在を
含めて、引数 1 個または 2 個をサポートします。参照先の型はサイズが既知でなければなりません。これらの
参照のモデルは `for<'a> Fn(&'a T) -> R` のような高階の境界を満たせます。高階の可変参照に対応する
モデルはありません。対象になるかどうかは、ジェネリックな関数の他の境界を満たせるかどうかにも依存します。
[ジェネリックな関数](#generic-functions)を参照してください。

これらのモデルは、検証対象の関数を任意のコールバックの結果に対してチェックします。特定のクロージャの
本体を実行したり、そのキャプチャ、変更、その他の副作用をモデル化したりはしません。検証が特定の
コールバックの実装に依存する場合は、手書きのハーネスを使ってください。これが `Success` の結果にとって
何を意味するかについては[その他の制限](#other-limitations)を、また
[#4994](https://github.com/model-checking/kani/issues/4994) も参照してください。

##### フォーマットトレイトの実装 {#formatting-trait-implementations}
`Debug`、`Display`、`Binary`、`Octal`、`LowerHex`、`UpperHex`、`LowerExp`、`UpperExp`、`Pointer` の
実装の `fmt` メソッドについては、Kani は一般的な[有界な `Formatter` モデル](#bounded-argument-generation)
ではなく、特別なハーネスを使います。このハーネスは、実装する型の非決定的な値を、出力を捨てるシンクへ
フォーマットします。`Formatter` はコアのフォーマット機構によって構築される（したがって常に有効な）もので、
`fmt` 実装の中のパニックや未定義動作は通常どおり検出されます。
これらのハーネスは実装する型について有界ではない（その値は `kani::any` で生成される）ので、デフォルトで
生成され、`--bounded-arguments` の影響を受けません。実装する型が [`Invariant`](#type-safety-invariants)
を実装している場合は、他の自動ハーネスと同じように、生成された値がそれを満たすと仮定されます。

現在の制限は次のとおりです。
- `Formatter` はデフォルトのフォーマットパラメータを持ちます。つまり、トレイトの素の指定子
  （`{:?}`、`{}`、`{:x}` など）で `format!` が作るものと同じです。そのため、`fmt` 実装がデフォルト以外の
  幅、精度、埋め文字、配置、符号、または代替フラグ（`{:#?}`、`{:#x}` など）のときにだけ通るコードパスは
  対象外です。
- シンクは決して失敗しないので、書き込みエラーを `?` で伝播する `fmt` 実装は、エラーのパスについては
  検証されません。
- ハーネスは `core::fmt` を経由するので、コアのフォーマット機構も `fmt` 実装と一緒に検証されます。
  そのため、報告された失敗が `core` の中の位置を指すことがあります。
- [関数契約](contracts.html)を持つ `fmt` メソッドは、この方法では扱われません。自動の契約ハーネスは
  関数を直接呼び出すので、その `&mut Formatter` 引数は有界な `Formatter` モデルから来ることになり、
  `--bounded-arguments` が必要です。

#### オプトインの過小近似 {#opt-in-under-approximations}

##### 有界な引数の生成 {#bounded-argument-generation}
一部の引数の型には有界な生成器が必要です。これには文字列や、要素がプリミティブの整数や浮動小数点数でない
スライスが含まれます。より大きな入力を必要とするバグは見逃されるので、これらの生成器は
**デフォルトでは無効**で、`--bounded-arguments` が必要です。このオプションによって対象になる関数は、
スキップされた関数の表で "Requires --bounded-arguments" という理由とともに報告されます。有界な値を使う
ハーネスには要約の表で **"(bounded)"** マーカーが付き、表の後の注記でこの制限が繰り返されます。

`--bounded-arguments` を指定すると、[有界でないプリミティブのモデル](#primitive-slices-and-vec)の対象外の
`&[T]`/`&mut [T]` 引数（`T` は `Arbitrary` を実装するか導出できるもの）や、`&str`、`&CStr`、`&ByteStr`、
`&Wtf8` 引数を持つ関数について、生成されるハーネスは非決定的な長さのスライスを作ります。その裏付けは、
ハーネス全体にわたって生存する非決定的なストレージです。デフォルトでは、スライスとバイト文字列は
**最大 16 要素**、文字列と WTF-8 文字列は**最大 4 バイト**、C 文字列は**最大 15 バイト**と終端の NUL です
（C 文字列はスライスの上限に従い、NUL の分だけ 1 少なくなります）。文字列は、上限までのすべての有効な
UTF-8 の内容を網羅します（生成される文字列は、非決定的なバイト列の有効な UTF-8 である最長の接頭辞です。
これは `String` の `BoundedArbitrary` 実装と同じ方法です）。上限が小さいのは、記号実行で UTF-8 について
推論するコストを反映したものです。WTF-8 文字列も同じ方法で、整形式の WTF-8 である最長の接頭辞として
生成されるので、対になっていないサロゲートのコードポイントを持つ値も網羅します。これらの上限は、
ループの展開のデフォルトの上限である 20 より小さくなるように選ばれているので、スライスに対するループは
デフォルトで完全に展開できます。

上限は `--slice-bound` と `--string-bound`（および後述の `--bounded-arbitrary-bound`）で設定できます。
この 3 つのフラグはいずれも `--bounded-arguments` を必要とし、正の上限だけを受け付けます。これらは
有界な生成器にだけ適用されます。有界でないプリミティブのスライスと `Vec` のモデルは、引き続き非決定的な
長さを使います。上限を大きくすると、より多くの入力を網羅できますが、ソルバのコストは高くなります。
上限が実際のループの展開の上限（`--default-unwind`、自動ハーネスではデフォルトで 20）より小さくない場合、
そのような引数に対するループは部分的にしか展開されません。設定した上限がそれに達すると、Kani は警告を
出します。要約の表の後に表示される注記で、その実行で実際に使われた上限が報告されます。

`&Formatter` と `&mut Formatter` の引数（これも `--bounded-arguments` が必要）は `any_formatter` で
生成されます。これは出力を捨てるシンクに対する `Formatter` で、すべてのフォーマットオプションが
非決定的であり、幅と精度はスライスの上限で制限されます。シンクは決して失敗しないので、書き込みエラーを
処理するパスには到達しません。

`core::str::pattern` のサーチャである `CharArraySearcher<'_, N>`、`CharArrayRefSearcher<'_, '_, N>`、
`CharSliceSearcher<'_, '_>`（`[char; N]`、`&[char; N]`、`&[char]` のパターンのためのサーチャ）も、
値渡しまたは参照渡しの引数としてサポートされます（これも `--bounded-arguments` が必要です）。ハーネスは、
非決定的な検索対象文字列（文字列の上限で制限された `&str`）に対して公開の `Pattern::into_searcher` API を
通じてサーチャを構築し、それから両端から非決定的な回数だけ進めます。そのため、途中まで進んだ状態の
サーチャも生成されます。サーチャは公開 API を通じてしか構築されず、進められないので、検索対象文字列が
有効な UTF-8 である限り、ライブラリ内部の不変条件を満たします。検索対象文字列は `&str` 引数と同じ
生成器から作られるので、現在の制限も同じです。verify-std のもとでは不正な UTF-8 になることがあり、
偽の失敗を引き起こすことがあります（[#5030](https://github.com/model-checking/kani/issues/5030) を参照）。
`CharArraySearcher` や `CharArrayRefSearcher` の検索文字列（needle）は非決定的な `[char; N]` で、その
長さ `N` は型によって固定されます。`CharSliceSearcher` の needle は、スライスの上限までの非決定的な
`&[char]` です。`N` はどのオプションでも制限されないので、大きな `N` を持つサーチャを受け取る関数には
大きな非決定的な needle が与えられ、`[T; N]` 引数の場合と同じように検証が遅くなることがあります
（ジェネリックな関数では、`N` は他の `usize` の const ジェネリックパラメータと同じ小さな値で
インスタンス化されます）。これらのサーチャの `Debug::fmt` メソッドは、
[フォーマットトレイトの実装](#formatting-trait-implementations)で説明した方法ではなく、サーチャと
`&mut Formatter` の両方を有界な引数として生成して、通常の関数として検証されます。

さらに（これも `--bounded-arguments` が必要）、型が [`BoundedArbitrary`](../bounded_arbitrary.html) を
実装する引数（たとえば `Vec<bool>`、`String`、またはそれを derive したユーザ型）について、ハーネスは
**デフォルトの上限 4** で（`kani::bounded_any` を使って）有界な非決定的な値を生成します。上限は
`--bounded-arbitrary-bound` で変更できます。同じ注意点があてはまります。
検証結果は上限までしか成り立ちません。上限が小さいのは、これらの値がヒープに割り当てられ、`String` では
UTF-8 の推論を伴うためです。どちらも記号実行にとってコストが高いものです。

これらの引数モデルは、入れ子のスライス参照（たとえば `&&[u8]`）や、ユーザ定義型の中のスライスの
フィールドは合成しません。ソースで定義された `Arbitrary` 実装なら、そのようなフィールドを与えられます。

##### コンストラクタに基づく生成 {#constructor-based-generation}

デフォルトでは、型が `Arbitrary` を実装していない場合、Kani はフィールドごとに値を合成します。
private なフィールドが表現の不変条件を持つ型（たとえば、検証済みの通し番号を詰め込んで格納する日付型）
では、フィールドをそのまま合成すると不変条件に違反する値ができることがあり、その型を生成するすべての
ハーネスで誤検知が起こります。`--constructor-args` を指定すると、Kani は代わりに、private なフィールドを
持つ構造体型の値を、その型自身のコンストラクタの 1 つを通じて生成します。優先順位は次のとおりです。

1. *アサーションで守られた表現コンストラクタ*。`unsafe`、`#[doc(hidden)]`、または `*_unchecked` という
   名前の、`Self` を直接返す関連関数で、その前提条件が、検証して返すのではなくアサーション
   （たとえば `debug_assert!`）として書かれているもの。Kani は非決定的な引数でその本体をインライン化し、
   すべての妥当性の記述、つまり `kani::assert` と `assert_unchecked` の呼び出し、パニックの入口、
   オーバーフロー（`Assert`）チェックを仮定に変換します。そのため、コンストラクタ自身のアサーションが、
   引数をクレートが有効とみなす値に絞り込みます。コンストラクタが、さらに別のアサーションで守られた
   ヘルパを呼び出す場合、それも再帰的にインライン化されます（深さと大きさには上限があります）。
   本体は呼び出されるのではなくインライン化されるので、ここでは可視性は関係ありません。
2. そうでなければ、*チェック付きの公開コンストラクタ*。`Self`、`Option<Self>`、`Result<Self, E>` を返す
   公開の関連関数で、非決定的な引数で呼び出されます（`Option<Self>`/`Result<Self, E>` の形では
   成功を仮定します）。

引数のないコンストラクタと、独自の型パラメータや const ジェネリックパラメータを導入するコンストラクタは
考慮されません。コンストラクタが独自のライフタイムパラメータを持つことは構いません。

`--constructor-args` はさらに *採掘された不変条件による絞り込み* も有効にします。生成された構造体と
列挙型の値は、`kani::assume` によって、Kani がその型自身のメソッドのアサーションから取り出せる条件を
満たすように制約されます（[採掘された不変条件](#mined-invariants)を参照）。
この絞り込みは、使えるコンストラクタを持たない型にも適用され、コンストラクタのインライン化より
論理式のコストが低くなります。

このオプションは過小近似になるのでオプトインです。このように値を生成または制約したハーネスには、
出力で "(ctor)" マーカーが付きます。したがって、このマーカーは上記のすべての仕組み、つまり
アサーションで守られたコンストラクタやチェック付きのコンストラクタ *と*、採掘された不変条件による
絞り込みを含み、検証結果が、選ばれた仕組みが許す値しか網羅しないことを示します。異なる値を必要とする
バグは見つかりません。また、チェック付きのコンストラクタ自体が一部の入力で（`Option`/`Result` で
拒否するのではなく）パニックする場合、それらの入力はハーネスの失敗になるので、このオプションはある種の
誤検知を別の種類の誤検知と引き換えにすることがある点にも注意してください。

例外が 1 つあります。独自の `Arbitrary` 実装を持つ型の値も、採掘された不変条件で絞り込まれますが、
そのハーネスには現在 "(ctor)" マーカーが付かず、注記も表示されません。
[#4995](https://github.com/model-checking/kani/issues/4995) を参照してください。

[健全性に関する注意点](#soundness-caveats)を参照してください。

### 仮定 {#assumptions}

仮定は、生成されたハーネスが探索する値と実行パスを制限します。
以下の仕組みは、Kani が関数の振る舞いをチェックする前に仮定を与えます。

#### 契約（requires） {#contracts-requires}

選ばれた関数が[関数契約](contracts.html)を持つ場合、Kani は `#[kani::proof_for_contract]` ハーネスを
生成します。関数の `#[kani::requires(...)]` 事前条件は入口で仮定されるので、検証はそれを満たす入力しか
網羅しません。たとえば、`#[kani::requires(x != 0)]` は自動の契約ハーネスから `x == 0` を除外します。

autoharness は、`unsafe fn` の宣言やその安全性のドキュメントから呼び出し側の義務を推論しません。
呼び出し側が除外すべき入力で関数をチェックしないように、それらの義務を事前条件として表現してください。
[生ポインタの例](#raw-pointers)を参照してください。

#### 型の安全性不変条件 {#type-safety-invariants}
型が [`Invariant`](https://model-checking.github.io/kani/crates/doc/kani/trait.Invariant.html) トレイトを実装している場合、
Kani は、自動ハーネスのために生成する非決定的な構造体と列挙型の値が、その型の安全性不変条件を守ると仮定します。
つまり、生成された各値 `v` は `v.is_safe()` を満たします。
Kani が構造体や列挙型の生成をフィールドごとに合成するときは、外側の型が `Invariant` を実装していなくても、
生成する構造体や列挙型のフィールドの安全性不変条件も仮定します。ソースで定義された `Arbitrary` 実装では、
入れ子の不変条件は、その実装か外側の型の `Invariant` によって強制しなければなりません。
ADT でない型（たとえばタプルや配列）に実装された不変条件は、現在は仮定されません。

これは [Unsafe Code Guidelines の安全性不変条件の定義](https://rust-lang.github.io/unsafe-code-guidelines/glossary.html#validity-and-safety-invariant)
と一致します。安全なコードは、受け取った値がその型の安全性不変条件を守っていると仮定してよいので、
不変条件に違反する入力に対して関数を検証すると、偽の反例が生じてしまいます。

#### レイアウトのニッチ {#layout-niches}

Kani が構造体や列挙型の `Arbitrary` を自動的に導出するときは、そのフィールドの値に対するコンパイラ定義の
制限を守らなければなりません。フィールドの基になる整数型は、フィールドの型そのものより多くの値を
許すことがあります。Kani は、コンパイラのレイアウト情報からフィールドの型の有効なスカラの範囲を読み取り、
値を生成するときに `kani::assume` の制約を加えます。

たとえば、`Arbitrary` 実装を持たない `Month` 型で、そのフィールドの型が基になる `u8` を `1..=12` に
制限しているとします。任意の `u8` を生成するだけでは、0 や 13 から 255 も許してしまいます。Kani は
制限されたフィールドを構築する前に、それを `1..=12` に制約するので、自動導出は有効な月の値だけを
作ります。これはフィールドの型で表現された制限に基づくものです。Kani は `Month` という名前から
それを推論するわけではありません。

コンパイラがレイアウトの最適化に使える不正なビットパターンは *ニッチ* と呼ばれます。`NonZeroU32` では、
0 がそのようなパターンです。その既存の `Arbitrary` 実装はすでに 0 を除外しているので、その生成パスでは
追加のレイアウトの仮定は冗長です。これが必要になるのは、そのような実装を持たない制限付きの型について、
生成を自動的に合成するときです。

これらの仮定は言語レベルで不正な値を除外し、生成器が表す有効な入力は保ちます。フラグや `Invariant` の
実装は不要で、"(ctor)" マーカーも付きません。不正なスカラ値による誤検知を防ぎますが、フィールド間の
追加の関係や、アプリケーションレベルの不変条件を推論するわけではありません。

#### 採掘された不変条件 {#mined-invariants}

多くの型は、`assert!(self.value >= 1)` のように、自身の固有メソッドの中のアサーションでフィールドに
関する条件を記述しています。Kani はこれらのアサーションを *採掘* でき、次の場合にその条件を型の
不変条件の候補として扱います。

- そのアサーションが、メソッドの通常の戻り、または該当する列挙型の match アームへのすべてのパス上に
  現れる（後支配）。
- その条件が、`self` のフィールドと定数に対する、サポートされた純粋な式である。Kani が式を取り出せる
  単純なフィールドのゲッタも含みます。
- 同じ条件が、少なくとも 2 つの異なるメソッドでアサートされている。

列挙型では、マッチしたバリアントから読み取った条件は、そのバリアントにだけ適用されます。
2 つのメソッドでのアサーションを要求することで、メソッドの事前条件を型の不変条件として扱ってしまう
危険は減りますが、その条件がすべての有効な値で成り立つことを証明するわけではありません。

採掘は現在、ジェネリック引数を持たない構造体型と列挙型に適用されます。メソッドは `self` を値、共有参照、
可変参照のいずれで受け取っても構いません。独自の型パラメータや const ジェネリックパラメータを持つ
メソッドは除外されます。

`--constructor-args` のもとでは、採掘された条件は生成された値について *仮定* されます。この入力の
絞り込みは、型がすでに `Arbitrary` を実装している場合にも適用されます。そのようなハーネスには現在
"(ctor)" マーカーが付きません（[#4995](https://github.com/model-checking/kani/issues/4995)）。
採掘された条件が実際には型の不変条件ではなくメソッドの事前条件だった場合、有効な値を除外してしまう
ことがあります。[健全性に関する注意点](#soundness-caveats)を参照してください。別のオプションである
[`--check-invariants`](#--check-invariants) は、採掘された条件を戻り値についてチェックします。

### チェック {#checks}

#### 未定義動作とパニック {#undefined-behavior-and-panics}

デフォルトでは、自動ハーネスは、選ばれた関数とそこから到達可能なコードに対して Kani の通常のチェックを
使います。これには、アサーション、パニック、整数オーバーフロー、ゼロ除算、不正なメモリアクセスが
含まれます。これらのチェックは、関数が契約を持つ場合にも実行されます。チェックが網羅する入力は、
上記の引数モデルと仮定によって決まります。

Kani が検出できる未定義動作の形とその現在の制限については[未定義動作](../../undefined-behaviour.html)を、
個々のチェックがどのように報告されるかについては[検証結果](../../verification-results.html)を
参照してください。

#### 契約（ensures） {#contracts-ensures}
契約を持つ関数について、自動の契約ハーネスは、関数の仮定された事前条件のもとで、戻るときに
各 `#[kani::ensures(...)]` 事後条件をチェックします。
たとえば、`#[kani::ensures(|result| result.is_safe())]` は、戻り値がその型の安全性不変条件を守っていることを
チェックします。

生成された入力について `Invariant::is_safe()` を仮定しても、出力についてそれが自動的にチェックされるわけでは
ありません。戻り値の安全性不変条件を検証するには、そのような事後条件を追加してください。
[関数契約](contracts.html)を参照してください。

#### `--check-invariants` {#--check-invariants}

`--check-invariants` を指定すると、Kani は検証した関数が返す値について、型の
[採掘された不変条件](#mined-invariants)をアサートします。サポートされる戻り値は、直接の `T`、`T` への参照、
または `Option<T>`/`Result<T, E>` の `Some(T)`/`Ok(T)` の中身です。
`T` は、条件を採掘できる構造体か列挙型でなければなりません。`None` と `Err` を返した場合は、中身は
チェックされません。チェックは、`Option<&T>` のような戻り値を再帰的に剥がしたり、タプルや配列の要素を
調べたり、変更された入力引数をチェックしたりはしません。

失敗のメッセージは、型と、採掘された条件をアサートしたメソッドを示します。採掘はヒューリスティックなので、
失敗が意味するのは、戻り値がそれらのメソッドがアサートした条件に違反しているということであり、それが
戻した関数のバグを示しているとは限りません。このオプションは `Invariant::is_safe()` ではなく採掘された
述語をチェックするもので、`--constructor-args` とは独立に使えます。契約を持つ関数では、これらの追加の
チェックは同じ事前条件のもとで実行され、事後条件のチェックを補います。

## 検証と結果の読み方 {#verifying-and-reading-results}

### 並列検証 {#parallel-verification}

autoharness は通常、多くのハーネスを生成するので、デフォルトでそれらを並列に検証します。
つまり、`--jobs`（スレッドプールのデフォルトのスレッド数で、通常は論理 CPU 1 つにつき 1 つ）と
`--output-format=terse` が渡されたかのように動作します。通常の `kani`/`cargo kani` による検証は
影響を受けず、デフォルトでは引き続き逐次的であることに注意してください。

デフォルトを変更するには次のようにします。
- `-j <N>` / `--jobs=<N>` は、同時に検証するハーネスの数の上限を決めます。各スレッドはそれぞれ CBMC の
  プロセスを実行するので、メモリのピーク使用量はスレッド数とともに増えます。実行中に利用可能なメモリを
  使い切ってしまう場合は `<N>` を小さくしてください。`--jobs=1` は terse 出力のまま逐次的に検証します。
- `--output-format=regular` は、Kani のデフォルトの、チェックごとのより詳しい出力で、ハーネスを逐次的に
  検証します（並列検証には terse 出力が必要です。詳しい出力が入り混じると読みにくいからです。そのため、
  `--jobs` を `--output-format=regular` と一緒に渡すとエラーになります）。

並列実行では、ハーネスの結果の各行の先頭に、それを出したスレッドが付き、結果は非決定的な順序で
届きます。最後に表示される要約の表は常に並べ替えられています。

### デフォルトの設定 {#default-settings}

自分で渡さない限り、`kani autoharness` は、1 つのハーネスが実行全体を止めてしまわないように、
2 つのデフォルトで自動ハーネスを検証します。

- 60 秒のタイムアウト（`--harness-timeout 60s` が渡されたかのように動作）。検証にこれより長くかかる
  ハーネスは停止され、失敗として報告されます。
- 20 のループの展開の上限（`--default-unwind 20` が渡されたかのように動作）。ループは最大 20 回まで
  展開されます。自動ハーネスには `#[kani::unwind]` アトリビュートがないので、`--unwind` を渡さない限り、
  この上限がすべてのループに適用されます。Kani の展開チェックは有効なままなので、より多くの反復が必要な
  ループは、黙って打ち切られるのではなく、展開アサーションに失敗します。

これらのデフォルトは自動ハーネスにだけ適用されます。`autoharness` が同時に検証する手動のハーネス
（`#[kani::proof]` や `#[kani::proof_for_contract]`）には、`kani`/`cargo kani` のもとで適用されるのと
同じ上限が適用されます。

どちらかの値を変えるには、そのオプションを明示的に渡してください。明示的な `--harness-timeout`、
`--default-unwind`、`--unwind` は、手動か自動かにかかわらずすべてのハーネスに適用されます。また、
手動のハーネスの `#[kani::unwind]` アトリビュートは引き続き `--default-unwind` より優先されます。

自動ハーネスが 1 つでも失敗すると、Kani は要約の表の後に、この 2 つのデフォルトについての注意を
表示します。失敗の原因が、関数のバグではなく、タイムアウトや展開の上限の不足かもしれないからです。
その場合は、より大きな値を試すか、可能であれば[ループ契約](./loop-contracts.html)を追加してください。
[有界な引数](#bounded-argument-generation)のデフォルトの上限は展開の上限より小さくなるように
選ばれていて、設定した上限がそれに達すると Kani は警告を出します。

検証そのものはデフォルトで並列に実行されます。[並列検証](#parallel-verification)を参照してください。

### 要約の表とマーカー {#summary-table-and-markers}

`kani autoharness` の実行は、3 つの段階で結果を表示します。

1. 検証の前に、`--quiet` が渡されていない限り、選ばれた関数とスキップされた関数の表
   （[スキップ理由](#skip-reasons)を参照）。
2. 検証中に、各ハーネスが終わるたびにその結果。
3. 検証の後に、`Autoharness Summary` の表と、それに続く
   `Complete - N successfully verified functions, M failures, T total.` という形の行。クレートに手動の
   ハーネスも含まれている場合、それらは同じ実行で検証され、`Manual Harness Summary` で別に報告されます。

要約の表には `Crate`、`Selected Function`、`Kind of Automatic Harness`、`Verification Result` の列があります。
行は関数名で並べ替えられ、成功が失敗より先に並びます。ジェネリックな関数では、`Selected Function` は
検証したインスタンス化を示します（たとえば `foo::<i32>`）。`Kind of Automatic Harness` は
`#[kani::proof]`、または関数が[関数契約](contracts.html)を持つ場合は `#[kani::proof_for_contract]` で、
次のマーカーの片方または両方が付くことがあります。

- **"(bounded)"**: 一部の引数が `--bounded-arguments` のもとで有界な値で生成されました。表の後の注記で、
  その実行で使われた上限（スライスの長さ、文字列の長さ、`BoundedArbitrary` の上限）を示し、結果は
  それらの上限までしか成り立たないことを繰り返します。
- **"(ctor)"**: 一部の値が、[`--constructor-args`](#constructor-based-generation) のもとで、型自身の
  コンストラクタの 1 つを通じて生成されたか、採掘された不変条件で制約されました。表の後の注記で、
  結果はそのコンストラクタを通じて到達できる値しか網羅しないことを繰り返します。
  独自の `Arbitrary` 実装を持つ型の採掘された不変条件だけで絞り込まれたハーネスには、現在マーカーが
  付きません。[採掘された不変条件のヒューリスティック](#mined-invariant-heuristic)を参照してください。
- **"(refcount)"**: 生成された値の一部に `Rc` や `Arc` が含まれていて、その参照カウントは有限個の状態
  だけでモデル化されています（[参照カウント](#reference-counts)を参照）。"(bounded)" と違い、これには
  オプションは不要です。`Rc`/`Arc` の引数はデフォルトで生成され、`is_bounded` ではなく
  `has_refcount_caveat` を設定します。表の後の注記でこの制限を繰り返し、関数ごとの
  "Checking function ..." のメッセージは "all possible inputs" に限定を付け、`--export-json` の文書は
  そのハーネスについて `has_refcount_caveat` を設定します。

これらのマーカーがどれも付いていない `Success` にも、[健全性に関する注意点](#soundness-caveats)で
説明する制限があります。

## 健全性に関する注意点 {#soundness-caveats}

`Success` の結果が意味するのは、ハーネスが生成したどの入力についても、Kani が失敗するチェックを
見つけなかったということです。以下は、それらの入力や検証したインスタンス化が、呼び出し側にできることを
すべて網羅しているわけではない場合です。そのため、`Success` でもバグを見逃すことがあります。Kani の
デフォルトのチェックでは、タイムアウトしたハーネスや、上限を超えるループの展開を必要とするハーネスは、
成功ではなく失敗として報告されます（[デフォルトの設定](#default-settings)を参照）。

### 単一の単相化 {#single-monomorphization}

ジェネリックな関数について、autoharness は単一のインスタンス化を検証します
（[ジェネリックな関数](#generic-functions)を参照）。各型パラメータは、その境界を満たす具体的な型の 1 つで
置き換えられ、各 `usize` の const ジェネリックパラメータは値 2 で置き換えられます。そのため、`foo::<i32>`
の `Success` は、`foo::<u8>` や `foo::<MyType>` も安全であることを意味しません。要約の表には常に
インスタンス化後の名前が表示されるので、どのインスタンス化が検証されたかがわかります。

`Fn`、`FnMut`、`FnOnce` で境界づけられた型パラメータは例外です。これらは、特定の 1 つのクロージャでは
なく、そのシグネチャを持つクロージャが返しうるすべての値を網羅するモデルでインスタンス化されます
（このモデルが網羅しないものについては[その他の制限](#other-limitations)を参照）。関数の他の型パラメータは、
引き続き 1 つの選択についてしか検証されません。

### 引数間の別名なし {#no-aliasing-between-arguments}
各参照、ポインタ、スライス、文字列の引数は、それぞれ独立した非決定的なストレージから生成されます。
そのため、autoharness は異なる引数 *どうしの* 別名（エイリアシング）を探索 *しません*。たとえば
`fn f(a: &T, b: &T)` に対して、生成されたハーネスは常に別々の割り当てへの 2 つの参照を渡すので、
呼び出し側は同じ参照を 2 回渡すことができるにもかかわらず、`a` と `b` が同じアドレスを共有することは
ありません（`core::ptr::eq(a, b)` は常に `false` です）。したがって、成功した自動ハーネスは、
[ジェネリックな関数](#generic-functions)で単一の単相化を検証することが過小近似であるのと同じように、
呼び出し側が制御する別名に関して過小近似です。これはすべての参照/ポインタ引数にあてはまり、
`--bounded-arguments` が導入する長さの上限とは無関係です。
引数間の、呼び出し側が制御する別名のモデル化は
[#4750](https://github.com/model-checking/kani/issues/4750) で追跡されています。

### 有界な引数 {#bounded-arguments}

"(bounded)" マーカーが付いたハーネスは、一部の引数に有界な非決定的な値を使います。これは
`--bounded-arguments` で有効になります（[有界な引数](#bounded-argument-generation)を参照）。
その結果は、それらの上限までの入力についてしか成り立ちません。より長いスライスや文字列、またはより大きな
`BoundedArbitrary` の値を必要とするバグは見つかりません。その実行で使われた上限は、要約の表の後の注記に
表示されます。プリミティブの整数や浮動小数点数のスライスや `Vec` のように、デフォルトで上限なしに
生成される引数は影響を受けません。

### 参照カウント {#reference-counts}

"(refcount)" マーカーが付いたハーネスは、参照カウントが有限個の状態だけでモデル化された `Rc`/`Arc` の
値を生成します。現在、生成されるすべての `Rc`/`Arc` は一意に所有されています
（`strong_count == 1`、`weak_count == 0`）。共有された状態の生成は
[#4752](https://github.com/model-checking/kani/issues/4752) で追跡されています。このような結果が
網羅するものと網羅しないものは次のとおりです。

- **正確なカウント。** 実際の呼び出し側は、他の強参照や弱参照をいくつ持つ `Rc` でも渡せますが、
  チェックされるのは一意に所有された状態だけです。特に、`get_mut`、`try_unwrap`、`into_inner`、
  `make_mut` の一意性チェックで共有されている場合の結果には決して到達せず、`strong_count` や `weak_count`
  を読むコード（たとえば `Rc::strong_count(&x) > 1`）は、カウント 1 と 0 についてしか検証されません。
- **他の保持者はいない。** 他の強参照や弱参照は存在しないので、他の保持者ができること、たとえば
  `RefCell` の借用を有効なままにしておく、`Weak` をアップグレードする、別のスレッドから値にアクセスする、
  といったことは何も網羅されません。
- **引数間の別名なし。** 異なる `Rc`/`Arc` の引数が割り当てを共有することはありません
  （`Rc::ptr_eq(&a, &b)` が真になることはありません）。
- **検出** は、参照、タプル、配列、スライス、`Box`、構造体や列挙型のフィールド、ジェネリック引数
  （`PhantomData` は除く）を含めて引数の型をたどります。そのため、型には `Rc`/`Arc` が現れるが、生成された
  値がそれを決して保持しないハーネスにもマーカーが付くことがあります。`kani::any::<Rc<T>>()` を呼び出す
  手動のハーネスにはマーカーは付きません。

### 空虚なコンストラクタ {#vacuous-constructors}

これは "(ctor)" マーカーが付いたハーネス、つまり `--constructor-args` を指定した実行にあてはまります
（[コンストラクタに基づく生成](#constructor-based-generation)を参照）。選ばれたコンストラクタが、生成される
型について *充足不能* な場合、つまり、どの引数でもアサーションに引っかかるアサーションで守られた
コンストラクタや、常に `None`/`Err` を返すチェック付きのコンストラクタである場合、生成された本体は
すべてのパスで `false` を仮定します。どの生成された値も満たさない採掘された条件も同じ効果を持ちます。
その結果、生成されたどの入力もテスト対象の関数に到達しなければ、そのハーネスは **空虚（vacuous）** です。
そのチェックはどれも失敗できません。Kani はその関数の呼び出しをカバーし
（`` autoharness: a generated input reaches `...` ``）、そのようなハーネスを
`` Vacuous harness: no generated input reaches `...` `` という行とともに失敗として報告します。契約を持つ
関数では、その `requires` 節は呼び出しの内側、カバーの後で仮定されるので、生成されたすべての入力を
除外する事前条件は空虚として報告されません。入力の一部だけで関数に到達するハーネス、たとえば中身を
生成できない `Option` 引数に `None` を渡すものは、通常どおり報告されます。除外された入力、たとえば
`Some` のパスは決してチェックされません。`--constructor-args` は `--output-format=old` とは組み合わせられ
ません。こちらは空虚なハーネスを検出できないからです。

### 採掘された不変条件のヒューリスティック {#mined-invariant-heuristic}

これは、採掘された不変条件が生成された値について仮定される、`--constructor-args` を指定した実行に
あてはまります（[採掘された不変条件](#mined-invariants)を参照）。そのようなハーネスには通常 "(ctor)"
マーカーが付きますが、絞り込まれた型が独自の `Arbitrary` 実装を持つ場合は付かないので、マーカーのない
`Success` でも影響を受けていることがあります。[#4995](https://github.com/model-checking/kani/issues/4995)
を参照してください。「2 つ以上のメソッドでアサートされている」という絞り込みはヒューリスティックであり、
型の不変条件であることの証明ではありません。2 つのメソッドが、普遍的な不変条件ではない *事前条件* を
共有している場合、それはすべての生成された値について仮定され、本来は有効な入力を除外することがあります。
これはバグを見逃す可能性につながります。これが許容されるのは、オプトインで過小近似である
`--constructor-args` の約束のもとでだけです。[#4763](https://github.com/model-checking/kani/issues/4763)
を参照してください。

### その他の制限 {#other-limitations}

以下の過小近似はデフォルトで適用され、要約の表はそれらが影響するハーネスにマーカーを付けません。

- **クロージャは副作用を持たない。** `Fn`/`FnMut`/`FnOnce` で境界づけられた型パラメータに使われる
  モデルは、呼び出しのたびに新しい非決定的な値を返しますが、何も変更しません。そのため、関数からも
  観測できる状態、たとえば `static` や、呼び出し側が引数としても渡す `Cell` を変更するクロージャは
  網羅されません。[#4994](https://github.com/model-checking/kani/issues/4994) を参照してください。
- **生ポインタは行儀がよい。** 生成される生ポインタは常にアラインされていて、解放済みのメモリを指す
  ことはなく、有効なときは常に初期化された値を指します。そのため、アラインされていないポインタや
  ダングリングポインタを必要とするバグは見つかりません（[生ポインタ](#raw-pointers)を参照）。
- **フォーマットはデフォルトのパラメータと、決して失敗しないシンクを使う。** `fmt` トレイトの実装の
  ハーネスは、デフォルトのフォーマットパラメータしか網羅せず、デフォルト以外の幅、精度、埋め文字、
  配置、符号、代替フラグは網羅しません。また、書き込みの失敗によるエラーのパスには決して到達しません
  （[フォーマットトレイトの実装](#formatting-trait-implementations)を参照）。`--bounded-arguments` のもとで
  使われる `&Formatter` のモデルも、決して失敗しないシンクに書き込みます。
- **仕様は仮定される。** 関数契約の事前条件と、`Invariant` を実装する型の `is_safe()` 述語は、生成された
  値について仮定されます。そのため、必要以上に強い事前条件や不変条件は、呼び出し側が渡しうる入力を
  除外してしまいます（[契約（requires）](#contracts-requires)と[型の安全性不変条件](#type-safety-invariants)
  を参照）。

## アーキテクチャ（コントリビュータ向け） {#architecture-for-contributors}

この節は、autoharness の動作を変更したいコントリビュータ向けです。作業は、コマンドラインを扱い検証を
実行するドライバ（`kani-driver`）と、クレートをコンパイルしながら関数を選んでハーネスを組み立てる
コンパイラ（`kani-compiler`）とに分かれています。

```text
┌──────────────────────────── kani-driver ────────────────────────────┐
│ args/autoharness_args.rs   CLI: --include/--exclude-pattern,        │
│                            --bounded-arguments, --constructor-args, │
│                            --check-invariants, --list, bounds       │
│ autoharness/mod.rs  setup_session(): parallel defaults, timeout,    │
│                     unwind, add_auto_harness_args() →               │
│                     --autoharness-* compiler flags                  │
│ call_single_file.rs: adds those flags to the kani-compiler call     │
└────────────────┬────────────────────────────────────────────────────┘
                 ▼
┌──────────────────────────── kani-compiler ──────────────────────────┐
│ kani_middle/codegen_units.rs                                        │
│   automatic_harness_partition()  → chosen / skipped (+reasons)      │
│   get_all_automatic_harnesses()  → AutomaticHarnessIntrinsic::<fn>  │
│                                    + gen_automatic_proof_metadata() │
│ kani_middle/transform/automatic.rs                                  │
│   AutomaticHarnessPass    dummy body → [contract init] args = any() │
│                           [assume invariants] f(args) [checks]      │
│   AutomaticArbitraryPass  T::any() for derivable types              │
│ codegen_cprover_gotoc → goto; KaniMetadata { autoharness_md, ... }  │
└────────────────┬────────────────────────────────────────────────────┘
                 ▼
┌──────────────────────────── kani-driver ────────────────────────────┐
│ postprocess_project(): chosen/skipped tables, --list stops here     │
│ harness_runner.rs: CBMC per harness → print_autoharness_summary()   │
└─────────────────────────────────────────────────────────────────────┘
```

1. **オプションとセッションのセットアップ**（`kani-driver`）。`args/autoharness_args.rs` は `autoharness`
   のオプションを定義し、検証します。`autoharness/mod.rs` の `setup_session` は関数契約とループ契約を
   有効にし、[並列検証](#parallel-verification)のデフォルトと
   [デフォルトのタイムアウトと展開の上限](#default-settings)を適用します。そして `add_auto_harness_args` が
   autoharness のオプションを `--autoharness-*` フラグに変換し、ドライバはそれを `kani-compiler` に渡します
   （`call_single_file.rs` を参照）。
2. **選択**（`kani-compiler`、`kani_middle/codegen_units.rs`）。
   `automatic_harness_partition` は、クレート内のすべての関数について、ハーネスを作るかどうかを決めます。
   ジェネリックな関数ではインスタンス化を選び、そうでなければ[スキップ理由](#skip-reasons)の 1 つを記録します。
   また、ハーネスが有界な値やコンストラクタに基づく値を使うかどうかも記録します。これらが "(bounded)" と
   "(ctor)" の[マーカー](#summary-table-and-markers)になります。選ばれた関数ごとに、
   `get_all_automatic_harnesses` は `kani_core` の `automatic_harness` 組み込み関数
   （`AutomaticHarnessIntrinsic` として印が付けられたもの）のインスタンスを作ります。その本体はまだ
   プレースホルダです。そして `gen_automatic_proof_metadata` でそのメタデータを生成します。
3. **ハーネスの本体**（`kani-compiler`、`kani_middle/transform/automatic.rs`）。
   `AutomaticHarnessPass` は、各プレースホルダの本体を実際のハーネスで置き換えます。関数が契約を持つなら
   契約の計装をセットアップし、[ハーネスの生成](#generating-harnesses)で説明したとおりに各引数を生成し、
   該当する[仮定](#assumptions)を仮定し、関数を呼び出し、[チェック](#checks)を追加します。
   `AutomaticArbitraryPass` は、`Arbitrary` を自動的に導出できる構造体と列挙型について `T::any()` を
   合成します。
4. **コード生成**。`codegen_cprover_gotoc` は、ハーネスを含むクレートを CBMC 用の goto プログラムに
   変換し、選ばれた関数とスキップされた関数は、クレートの `KaniMetadata` の `autoharness_md` フィールドに
   格納されます。
5. **結果**（`kani-driver`）。`autoharness/mod.rs` の `postprocess_project` は、選ばれた関数とスキップされた
   関数の表を表示します。`--list` の場合、実行はここで終わります。そうでなければ、`harness_runner.rs` が
   各ハーネスに対して CBMC を実行し、その後 `print_autoharness_summary` を呼び出して
   [要約の表](#summary-table-and-markers)を表示します。
